Сервис резервирования ткани под производственные заказы швейной фабрики. На складе лежат рулоны с артикулом и метражом, технолог создает заказ (например 200 футболок по 1.4 метра трикотажа), сервис отрезает нужный метраж из подходящих рулонов, не уходит в минус при параллельных запросах и сообщает остальной системе о резерве и отмене через outbox

Стек Python 3.12, FastAPI, SQLAlchemy 2 в async режиме поверх asyncpg, Alembic, PostgreSQL 16, uv. Код лежит в src/fabric Домен в inventory/domain не знает ни про FastAPI, ни про SQLAlchemy, это проверяет отдельный тест

Настройки берутся только из переменной DATABASE_URL, пример в .env.example, значение по умолчанию смотрит на postgres из docker compose

```
uv venv
uv sync
docker compose up -d db
uv run alembic upgrade head
uv run uvicorn fabric.main:app --reload
uv run python -m fabric.relay
```

запуск в докере

```
docker compose up --build
```

Тесты идут на настоящем PostgreSQL через testcontainers, нужен только запущенный Docker. Порог покрытия 85 процентов прописан в pyproject.toml

### Блокировки
Резерв берет заказ и все рулоны его артикула через SELECT ... FOR UPDATE в порядке возрастания id, отмена блокирует свои рулоны в том же порядке, поэтому транзакции встают в очередь и не ловят deadlock. Я выбрал пессимистичную блокировку, потому что транзакции короткие, а конкуренция за рулоны одного артикула высокая, и с оптимистичной блокировкой и тремя повторами часть запросов получала бы 409 не от нехватки ткани, а от проигранной гонки. Колонка version осталась и проверяется при update как страховка, если блокировку однажды забудут взять

### Идемпотентность
Ключ из заголовка Idempotency-Key пишется в idempotency_keys в той же транзакции, что и резерв или отмена. Второй запрос с тем же ключом ждет на уникальном индексе, пока первый закоммитится, и получает сохраненный ответ без повторного выполнения. Тот же ключ с другим телом или на другом эндпоинте дает 409. Если сценарий закончился ошибкой, ключ не сохраняется и запрос можно повторить

### Outbox
События MaterialReserved и ReservationCancelled пишутся в таблицу outbox в той же транзакции, что и изменение заказа. Relay раз в секунду берет до 100 строк через FOR UPDATE SKIP LOCKED и отдает их издателю, по умолчанию это JSON строка в логе. Ошибка издателя увеличивает attempts, после пяти попыток событие считается мертвым, больше не берется и попадает в лог с уровнем error. Издатель спрятан за протоколом EventPublisher, RabbitMQ подключается новой реализацией без изменений в домене

### Доставка at least once
Если relay упадет после публикации, но до коммита, событие уйдет еще раз. Потребитель должен дедуплицировать по event_id, проще всего хранить обработанные id в своей таблице с уникальным индексом и пропускать повторы. Порядок между событиями разных заказов не гарантирую

### Стратегия подбора
Сначала ищу самый маленький рулон, которого хватает на весь остаток потребности, так большие рулоны не дробятся зря. Если такого нет, добиваю начатые рулоны по возрастанию остатка и после каждого снова ищу подходящий. Частичный резерв запрещен, либо весь метраж, либо 409

Метры хранятся в numeric(12, 2), в коде это Decimal. Значение с тремя знаками после запятой я отклоняю, а не округляю, иначе сумма строк резерва могла бы не сойтись с требуемым метражом

Логи пишутся JSON строками стандартным logging. У каждого запроса есть request_id, он же возвращается в заголовке X-Request-ID.

Read модель остатков по артикулам, сейчас остаток каждый раз считается суммой активных строк резерва, и на большом складе это станет узким местом. Плюс чистку старых idempotency_keys по created_at
